\begin{abstract}
We present \textsc{ZPDPatch}, a trajectory-supervised repair technique that mines execution improvements as training targets and selects generated programs by execution. Program repair for programming exercises benefits from correct peer solutions, learned transformations, and execution feedback. Submission histories offer an additional signal: earlier unsuccessful revisions can distinguish users who reach the same current program. However, a history-aware system can improve simply by generating more candidates, and changing its target rule also changes its training population. Establishing a trajectory-specific benefit therefore requires separate controls for target construction, input history, and candidate breadth. \textsc{ZPDPatch} mines three evidence relations, trains independent policies, and selects a validation-frozen portfolio with an optional edit budget. We evaluate 997 Seen and 250 problem-held-out Python inputs, replicate matched-target training on 181 student-held-out Java trajectories, and separately examine completed development runs. Matched terminal targets repair 19.2 and 11.2 percentage points more Python inputs than progress targets; progress-target repairs retain 5.6 and 6.5 more token points on joint successes, and Java reproduces both directions. Three fixed candidate draws alone add 15.1 Seen points, while the completed history-specific improvements fail their fixed controls. The mixed portfolio repairs 61.5\%/74.8\% of Seen/Unseen inputs, versus 72.0\%/81.2\% for the retained current-only terminal triple; retrieval-based generation reaches 80.2\% on Seen.
\end{abstract}

\section{Introduction}
\label{sec:introduction}
Automated program repair (APR) generates changes to a failing program and validates them against an executable specification~\cite{gazzola2019automatic,monperrus2018automatic,weimer2009automatically,legoues2012genprog}. For programming exercises, a repair can provide code-specific feedback beyond an online judge's verdict~\cite{keuning2018systematic,joshi2023repair,zhang2024pydex}. Earlier submissions additionally record attempted strategies, repeated errors, and tests already passed. Should a repair depend on this path to the current code, rather than on that code alone?

Existing methods cluster, align, or normalize correct peer programs~\cite{gulwani2018automated,wang2018search,hu2020re}, or use learned generation, retrieval, diagnostics, and repair conversations~\cite{joshi2023repair,zhang2024pydex,liu2024fastfixer,yang2024cref,orvalho2025counterexample,dai2026learner}. These are strong alternatives: LSGen repairs 80.2\% of our Seen inputs. Their success nevertheless does not establish that earlier submissions add information beyond current code, adaptation, and additional generation opportunities.

We define \emph{trajectory-conditioned repair} as repair whose supervision or generated change depends on the sequence leading to the current submission. Two users may reach similar code after different failed revisions, suggesting different next changes. The Zone of Proximal Development (ZPD) motivates support informed by prior activity~\cite{cole1978mind,murray2002toward,chounta2017grey,schulze2024beyond}. Our testable hypothesis is narrower: authentic history should improve executed repair over current-code, shuffled-history, and other-user controls without increasing regressions or unresolved outcomes. An observed sequence does not measure mastery, and a smaller patch does not establish learning.

A second use of a trajectory changes the training target: later improvements can replace the eventual accepted solution. Our terminal rule emits 40,454 examples, whereas the progress rule emits 21,416, changing both targets and source frequencies. Candidate breadth also matters: three fixed stochastic draws add 15.1 Seen repair-rate points over the expected single draw. A gain over one terminal adapter therefore cannot isolate relational supervision or authentic history. We use source-matched retraining, same-target independent seeds, and matched candidate budgets to distinguish these explanations.

We present \textsc{ZPDPatch}: \emph{Mine} constructs terminal, strict-verdict, and test-progress relations; \emph{Train} fits independent policies; and \emph{Select} freezes a validation-selected checkpoint triple. An execution gate returns a repair or retains current code, optionally within an edit budget. Separate controls replace targets with matched peer programs, remove or perturb histories, and hold draws fixed. These controls are not unreported ingredients of the deployed mixed portfolio.

On 997 Seen and 250 problem-held-out Python inputs, matched terminal targets repair 19.2 and 11.2 points more inputs, while progress targets retain 5.6 and 6.5 more token points on joint repairs. Student-disjoint Java retraining reproduces both directions. However, Mixed reaches 61.5\%/74.8\%, below the current-only terminal triple's 72.0\%/81.2\%. Subsequent development improves generic execution selection but yields no candidate satisfying every authentic-history adoption condition. We retain the existing version: the evidence supports a target-induced coverage--locality tradeoff, not the proposed history-specific advantage.

\noindent\textbf{Contributions.} We summarize our contributions as follows:
\begin{itemize}
\item \textbf{Problem and hypothesis:} We distinguish trajectory-derived targets from authentic-history conditioning and candidate breadth, and formulate controls that can reject a history-specific explanation even when aggregate repair coverage increases.
\item \textbf{Technique:} We specify Mine, Train, and Select, including the three retained-submission rules, exact validation portfolio selection, and an execution gate with explicit fallback and edit-budget semantics.
\item \textbf{Evaluation:} We separate target, provenance, decoder, checkpoint, and history effects on Python and Java, report the completed development failures under their original criteria, and provide a claim--evidence map to the retained experimental artifacts.
\end{itemize}

\section{Preliminaries}
\label{sec:preliminaries}
\subsection{Submissions and Execution Evidence}
\label{sec:formulation}
For a problem \(p\), a submission state is a tuple \(s=(c,v,o)\), where \(c\) represents complete source code, \(v\) denotes the recorded online-judge verdict, and \(o\) maps each available testcase identifier to its re-executed outcome. The problem context \(d_p\) contains the statement and resource limits, and \(\mathcal E_p\) is the available test suite. A trajectory \(\tau=[s_1,\ldots,s_n]\) orders submissions by one user on one problem. The canonical dataset ends each trajectory at its first recorded acceptance; this endpoint is the final accepted submission within the retained trajectory, not a later post-acceptance revision. Recorded verdicts and replayed outcomes remain distinct fields, because runtime versions and execution variability can change a program's observed behavior.

A training example pairs input \(x=(d_p,h_i)\) with later code \(y\), where \(h_i\) is the permitted submission prefix ending at the current state. A target constructor determines both the retained prefix and its target. At inference, the current program is always available; a history-conditioned prompt also includes earlier observed submissions, whereas a current-only prompt does not. The future accepted program is a training target or an offline assessment reference, never part of the inference prompt. A \emph{terminal target} is the accepted endpoint. A \emph{progress target} is the next retained state under an execution-evidence rule and can itself be accepted. We reserve \emph{intermediate target} for a retained nonterminal state; the Progress dataset is not restricted to such states.

\subsection{Generate-and-Validate Selection}
\begin{algorithm}[h]
\caption{Execution-Gated Repair}
\label{alg:generic}
\small
\KwIn{Current program ($c$), context ($x$), ordered generators ($S$), tests ($\mathcal E$), edit budget ($B$).}
\KwOut{Returned program ($c^*$).}
$c^* \gets c$; $q^* \gets \textsc{Execute}(c,\mathcal E)$\;
\ForEach{$v\in S$}{
 $z \gets \textsc{Generate}(v,x)$\;
 \If{$B<\infty$ and $\mathrm{ted}^{\dagger}(c,z)>B$}{\textbf{continue}\;}
 $q \gets \textsc{Execute}(z,\mathcal E)$\;
 \If{$q=1$}{\Return $z$\;}
 \If{$(q,-\mathrm{ted}^{\dagger}(c,z))>(q^*,-\mathrm{ted}^{\dagger}(c,c^*))$}{
 $c^*\gets z$; $q^*\gets q$\;
 }
}
\Return $c^*$\;
\end{algorithm}

Algorithm~\ref{alg:generic} describes the common controller. For now, we set aside how the generators \(S\) are trained and selected. Line 1 executes the current code and makes it the fallback. Each generator emits a complete candidate, which is excluded if it violates a finite edit budget. Execution then determines whether to accept immediately or update the best partial repair. The final return preserves the fallback when no candidate improves its score. Here \(q\) is the fraction of tests passed, and \(\mathrm{ted}^{\dagger}\) is AST tree edit distance when both changed programs parse, zero for unchanged code, and infinity otherwise. An unrestricted budget bypasses the distance check, allowing syntax repair; a finite budget rejects changes whose source distance is undefined.

This controller exposes three independent decisions: the source of generators, their input context, and the number of generation opportunities. Reference-based repair changes generation by supplying aligned peer programs~\cite{gulwani2018automated,wang2018search,hu2020re}. Neural and language-model repair changes it through training and prompting~\cite{tufano2019empirical,lutellier2020coconut,joshi2023repair,zhang2024pydex}. Iterative methods also update context with execution feedback~\cite{yang2024cref,orvalho2025counterexample}. These are not all supervised-learning methods and need not share a target constructor. Our comparisons isolate specific implementations rather than assuming that all prior systems train on accepted endpoints.

\subsection{Limitation and Goal}
\label{sec:limitation}
Consider three wrong-answer submissions with pass vectors \((1,0,0)\), \((1,1,0)\), and \((0,1,1)\), followed by an accepted state. The second preserves every previously passed test and gains another; the third gains a test but loses the first. Verdict-only filtering cannot distinguish them, while test-wise progress retains the second but not the third relative to it. Terminal supervision instead pairs each failed source independently with the acceptance. This example illustrates different training signals, not evidence that the intermediate change is smaller or easier for a learner.

Table~\ref{tab:rules} shows why exchanging a target rule is not a one-variable intervention: example counts and source frequencies change together. The relation-level comparison characterizes complete policies, whereas matched-source retraining estimates target replacement on a common population. A scoped audit of eight directly related educational-repair studies also motivates explicit candidate accounting: five evaluate or deploy multiple generation opportunities, and three of those five lack a matched single-opportunity quantity~\cite{zhang2024pydex,koutcheme2024benchmarking,yang2024cref,orvalho2025counterexample,dai2026learner}. This is a purposive evidence map, not a systematic review or a claim that adaptive iterations equal independent draws. Its coding rules remain in the artifact.

These observations motivate constructing auditable trajectory-based supervision and determining whether it improves repair beyond current-code and budget-matched alternatives. Correctness, source preservation, and history specificity are separate outcomes. A smaller patch does not satisfy a correctness objective, and higher pooled correctness alone does not satisfy a history-specific objective. The canonical evaluation measures these dimensions separately; later development additionally requires non-increasing regressions and unknown outcomes under fixed controls.

\begin{algorithm}[h]
\caption{\textsc{ZPDPatch}: Mine, Train, Select}
\label{alg:tool}
\small
\KwIn{Training trajectories ($H$), cached evidence ($O$), validation inputs ($U$), seeds ($\Sigma$), portfolio size ($k$), edit budget ($B$).}
\KwOut{Frozen ordered checkpoint portfolio ($S$).}
\tcc{Step 1. Mine}
$(D_A,D_S,D_P)\gets(\emptyset,\emptyset,\emptyset)$\;
\ForEach{$\tau\in H$}{
 $D_A\gets D_A\cup\mathsf{TerminalPairs}(\tau)$\;
 \ForEach{$\rho\in\{S,P\}$}{
  $R\gets[s_1]$\;
  \ForEach{$s_t\in[s_2,\ldots,s_n]$}{
   \If{$\mathsf{Improves}_{\rho}(R[-1],s_t;O)$}{
    $D_\rho\gets D_\rho\cup\{(R,c_t)\}$\;
    $R\gets R\mathbin{\|}[s_t]$\;
   }
  }
 }
}
\tcc{Step 2. Train}
$V\gets\emptyset$\;
\ForEach{$\rho\in\{A,S,P\}$ and $\sigma\in\Sigma$}{
 $V\gets V\cup\{\mathsf{Train}(D_\rho,\sigma)\}$\;
}
\tcc{Step 3. Select}
\ForEach{$v\in V$}{ $R_v^B\gets\mathsf{Validate}(v,U,B)$\; }
$S\gets\mathsf{Select}(\{R_v^B\}_{v\in V},k)$\;
\Return $\mathsf{FreezeAndOrder}(S)$ \tcp*{input to Algorithm~\ref{alg:generic}}
\end{algorithm}

\subsection{Main Algorithm}


Algorithm~\ref{alg:tool} returns a checkpoint portfolio, not a repaired test program. It mines terminal pairs and retained scans, trains one adapter per relation--seed combination, and searches validation subsets before freezing their order. Deployment uses Algorithm~\ref{alg:generic}. The primary configuration uses three seeds and \(k=3\); breadth and pool controls explicitly vary these opportunities.

\subsection{Mine}
The goal of Mine is to make every supervision pair traceable to an observed source and a later submission. Submissions are grouped by problem and user, chronologically ordered, and cut at the first acceptance. Canonical normalization removes consecutive duplicates while preserving the source code used for generation and execution. The builder imposes no maximum history or transition count. A whole-trajectory filter instead excludes a trajectory before splitting if any required prompt--target configuration exceeds 4,096 tokens. Exclusion changes the evaluated population; it never cuts off a program or history and presents the fragment as complete.

The coarse severity function assigns 0 to accepted (AC), 1 to wrong answer (WA), 2 to time or memory limit exceeded (TLE/MLE), 3 to runtime error (RE), and 4 to compile error (CE); unrecognized and internal outcomes occupy the most severe category. This is an operational ordering, not semantic distance to correctness. Strict compares recorded verdicts. Progress additionally compares replayed outcomes when the recorded verdict strings agree. Its cache must be complete, and compared vectors must have equal, nonempty testcase keys. Provenance includes problem, code, tests, and execution configuration. Infrastructure uncertainty in later development is reported as unknown, not converted into a favorable repair label.

For equal testcase universes, \(o_t\prec_\times o_r\) holds when every test in \(o_t\) has severity no greater than its counterpart in \(o_r\), with a strict decrease on at least one. The improvement predicates are:
\begin{equation}
\begin{aligned}
\mathsf{Improves}_S(r,t)&\iff \mathrm{sev}(v_t)<\mathrm{sev}(v_r),\\
\mathsf{Improves}_P(r,t)&\iff \mathsf{Improves}_S(r,t)\\
 &\quad\lor\ (v_t=v_r\land o_t\prec_\times o_r).
\end{aligned}
\label{eq:progress}
\end{equation}
Intuitively, Equation~\eqref{eq:progress} retains coarse improvements and progress hidden by an unchanged verdict. A severity improvement such as RE to WA need not increase the pass fraction, and a verdict-improving edge does not require test-wise dominance. The mined relation supplies supervision, not a deployment-safety guarantee.

Answer emits an independent pair for each non-AC source and the accepted endpoint. Thus \([s_1,\ldots,s_9]\) yields \(([s_1],c_9),\ldots,([s_8],c_9)\); it does not expose accumulated prefixes to Answer training. Strict and Progress start with \(R=[s_1]\), compare each later state with the \emph{last retained} state, and append it only when the predicate holds. Before appending \(s_t\), the builder emits \((R,c_t)\). For WA, improved WA, AC, Strict emits \(([s_1],c_3)\), whereas Progress emits \(([s_1],c_2)\) and \(([s_1,s_2],c_3)\). The accepted endpoint remains eligible in both rules. Although Strict's pairwise predicate is contained in Progress's, their independently scanned edge sets need not be nested.

Chronological indices strictly increase, so construction terminates without cycles. With fixed-key evidence, retained edges also decrease the appropriate verdict/test severity rank. These are builder invariants, not evidence of a learned ZPD effect. Binary accepted/non-accepted mining retains 14,027 of 16,973 Strict pairs and 18,009 of 21,416 Progress pairs. Models retrained on them agree with the canonical ones on 84.6\% and 87.5\% of Seen repair decisions (Section~\ref{sec:generality}), so we read the ranking as operational rather than universal.

\subsection{Train}
The goal of Train is to learn each relation independently while keeping model and optimization comparable. The implementation fine-tunes Qwen2.5-Coder-7B-Instruct with 4-bit QLoRA~\cite{hui2024qwen2,dettmers2023qlora}. Adapters have rank 16, scaling 32, and dropout 0.05, targeting attention and feed-forward projections. Canonical training uses one epoch, learning rate \(2\times10^{-4}\), and seeds 2027--2029. Assistant target tokens supply cross-entropy loss. The role-neutral prompt contains the statement, limits, permitted submissions, execution/edit summaries, and a request for a complete solution. It names neither the rule nor a preferred patch size, so specialization must come from the data rather than explicit policy instructions.

Targets are future submissions available offline; inference inputs contain only observed states. Current-only controls reset positions and remove earlier entries, preventing length leakage through position labels. Answer training is already single-source, so supplying history at inference creates a distribution change. The history-removal retraining control instead holds targets fixed and changes earlier-submission serialization. Source-matched target training holds current input and count fixed. These designs answer different questions and are not pooled into one claim about history.

The paired-target control inner-joins records by problem, user, submission identifier, and exact current code, retaining sources with distinct Answer and Progress targets. Its 7,389 training and 931 validation examples per condition use identical current-only inputs. The separate peer control requires another user on the same problem and in the same split, with exactly equal target execution evidence. For deterministic semantic-token diff distance \(d\), the discrepancy \(\delta=|d(c,y_v)-d(c,y_u)|\) must satisfy \(\delta\le2\) or \(\delta/\max(1,d(c,y_u))\le0.1\). Scarce evidence groups are visited first; ties prioritize distance discrepancy, reuse, and identifier, with donor reuse capped at three. This greedy rule yields 5,231 training and 306 validation examples per condition. Equal outcomes and nearby distances do not equate structure or style, so its measured effect belongs to the entire replacement rule, not isolated provenance.

\subsection{Select}
The goal of Select is to deploy a bounded portfolio chosen without final-test outcomes. For validation inputs \(U\), let \(R_v^B\) be inputs repaired by checkpoint \(v\) within edit budget \(B\). Selection maximizes:
\begin{equation}
 f_B(S)=\frac{1}{|U|}\left|\bigcup_{v\in S} R_v^B\right|,\qquad |S|=3.
\label{eq:portfolio}
\end{equation}
Intuitively, Equation~\eqref{eq:portfolio} rewards complementary successes, not low training loss or the presence of every relation. Validation uses one fixed-hash trajectory from each of 461 eligible problems. The mixed pool has nine checkpoints and 84 triples; requiring one checkpoint per relation instead permits 27. The primary unconstrained mixed choice is Answer2027, Answer2028, and Progress2027. The relation-constrained choice is a different condition. Answer-9Choose3 receives nine terminal checkpoints and the same 84-triple search. Ties use recorded pass-rate, improvement, and deterministic identifier priorities. Budget-indexed selection repeats the declared objective at \(B\in\{5,10,20,40,80,160\}\), without choosing a budget from test results.

Selected checkpoints and order are frozen. Each emits at most one independent candidate, and the first observed acceptance stops generation. If none passes all tests, Algorithm~\ref{alg:generic} prioritizes pass fraction and then smaller distance. Because unchanged code is feasible, for the same fixed execution measurements the returned pass fraction cannot decrease, and a finite edit budget cannot be exceeded. This is not per-test non-regression: equal fractions can conceal gains and losses on different tests. It also does not guarantee non-regression under fresh execution, an unseen suite, or resource variability. Development explicitly measures these stronger failure modes.

For fixed independent candidates, order changes calls and patch identity but not the existence of an eligible acceptance. Stored candidates permit exact selection replay, not a guarantee of generation quality. Terminal pairing is linear in trajectory length; replaying \(n\) submissions on \(m\) tests requires \(O(nm)\) executions and evidence storage. The 84-triple search is bounded at our pool size, not a scalable optimizer for arbitrary pools.



\section{Experiments}
\label{sec:experiment}
We evaluate the retained implementation and completed development evidence through five research questions:
\begin{itemize}
\item \textbf{RQ1: Repair effectiveness.} Which configuration provides the strongest unrestricted repair performance?
\item \textbf{RQ2: Target construction and locality.} How do matched targets affect correctness and source preservation?
\item \textbf{RQ3: Component efficacy.} What do candidate breadth, checkpoint identity, and serialized history contribute?
\item \textbf{RQ4: Generality.} Which findings replicate across problems, prefixes, scales, and Java populations?
\item \textbf{RQ5: Development diagnosis.} Do completed history-specific modifications satisfy their fixed adoption criteria?
\end{itemize}

\subsection{Experimental Settings}


\noindent\textbf{Benchmarks.} Table~\ref{tab:data} describes the Project CodeNet Python800 corpus~\cite{puri2021project}. We retain trajectories with at least three submissions, a non-AC state before the first acceptance, and an accepted endpoint in the benchmark reference set. Users must appear in at least three problems, and retained problems contain at least two trajectories. The refined corpus has 546 problems, 21,454 trajectories, 99,432 submissions, and 10,088 tests. Whole-trajectory 4,096-token filtering removes 3,660 trajectories before splitting. Problems ranked by eligible trajectory count supply the top 90\% to Seen (492) and the remaining 54 low-resource problems to Unseen. Seen trajectories are split 80:10:10 within every problem, retaining at least one in each partition. Users can overlap across Seen partitions; ``--'' avoids counting repeated users as distinct people in the total row.

The primary endpoint is the last recorded non-AC submission of an eventually successful trajectory. Runtime eligibility requires the current program to remain non-AC and the recorded accepted endpoint to pass the available tests on replay. This leaves 997 of 1,754 Seen test trajectories, from 328 problems, and 250 of 259 Unseen trajectories, from all 54 problems. Excluded trajectories do not enter the denominator. CodeNet users are online-judge participants, not a verified classroom population. We also use TIKTOC's release of authentic CS1 Java CodeWorkout submissions and tests~\cite{duan2024tiktoc}: 1,125 trajectories from 224 students and 17 exercises, with 181 test trajectories from 33 held-out students. A separate exercise split has 10/3/4 train/validation/test exercises and 605/216/304 trajectories. These populations remain separate from the Python estimates.

\noindent\textbf{Baselines.} Zero-shot uses the same base model without fine-tuning and appends verdict/pass-count feedback after failure. LSGen retains repair-pair filtering, edit-vector retrieval, diff-guided generation, and re-retrieval~\cite{dai2026learner}; its same-problem Seen-Train references are unavailable under our Unseen information constraint, so that condition is not evaluated. Answer-1 uses one terminal checkpoint. Answer-3Seed uses seeds 2027--2029 on the same 40,454 terminal pairs, controlling independent training without heterogeneous targets. Answer-9Choose3 adds seeds 2030--2035 and selects three from nine. History and current-only prompts are explicitly labeled. Mixed-9Choose3 denotes the primary unconstrained \textsc{ZPDPatch} pool. Current-only reselection from the mixed pool chooses the same three Answer checkpoints as Answer-3Seed, not a relation-mixing improvement.

\noindent\textbf{Other settings.} Canonical generation and training use a single NVIDIA RTX 5090. Candidates execute in network-disabled containers with Python or Java 21, a 2.5-second per-test timeout, and a 2GB memory limit. The primary comparison permits at most three generations, each capped at 4,096 output tokens; this cap differs from pre-split whole-trajectory filtering. Historical Transformers deployment and the later vLLM factorial are separate inference stacks. Decoder-matched contrasts remain within a stack. Adapters use three declared seeds, but a selected portfolio's outcome is not a mean over three independent test experiments.

Repair Rate (RR) is the fraction of eligible inputs whose returned program passes every test. Pass Rate (PR) averages passed-test fractions; Improvement Rate (IR) records an increased fraction. AST tree edit distance (TED) measures current-to-returned change~\cite{zhang1989simple,pawlik2016tree} and is undefined when either program does not parse. Such cases remain in unrestricted RR but not defined-TED summaries; finite gates reject undefined-distance changes. Token and nonempty-line retention measure the original code retained, not learning value. Locality contrasts use jointly repaired instances to avoid unrelated success sets, but remain conditional on joint success.

Paired intervals resample problems 10,000 times with recorded seeds; Java reports student- and exercise-cluster alternatives~\cite{efron1979bootstrap}. We distinguish instance-weighted RR from equal-problem-weight contrasts and report Wilson intervals, exact McNemar tests, and Holm correction where specified~\cite{wilson1927probable,mcnemar1947note,holm1979simple}. Protocols and amendments identify when each control was frozen; the extended study was not externally preregistered. Repeatedly inspected development results are exploratory even when an individual run uses fixed gates. We use the preserved whitespace-sensitive corrections rather than mixing original and corrected counts.

\noindent\textbf{Research process.} OpenAI Codex assisted with design, dataset and analysis code, remote orchestration, diagnostics, and manuscript preparation under author instructions. Automated agents executed authorized jobs and inspected saved outputs; we do not claim authors manually ran every job. Outcomes come from retained execution records and analyses, not generated prose. \noindent\textbf{Matched targets.} Table~\ref{tab:targets} changes the target while holding current inputs and training counts fixed. The paired population is restricted to sources with distinct targets, however, and does not estimate an effect for all CodeNet submissions. Moreover, a Progress target can itself be accepted. The intervention is the retained-evidence target rule, not a clean contrast between exclusively incorrect and exclusively correct targets.

Progress's locality benefit is visible on joint successes. Among 299 Seen and 154 Unseen jointly repaired inputs, 278 and 134 have defined source-to-repair TED for both methods. It also cannot support a claim that one's own trajectory is uniquely necessary: matched peer targets improve coverage in this control.

\subsection{RQ3: Component Efficacy}
\noindent\textbf{Fixed candidate breadth.} For three stored draws with success indicators \(a_{ij}\), the expected uniformly selected one-draw success for input \(i\) is \(\frac{1}{3}\sum_j a_{ij}\), whereas the three-draw union succeeds when \(\max_j a_{ij}=1\). Their paired difference isolates additional opportunities within the identical candidate set. Replacing greedy decoding by one stochastic draw costs 7.6 points [-9.81, -5.41], whereas execution-selecting three of those identical fixed draws contributes 15.1 points [13.48, 16.76] on Seen. This is a descriptive decomposition of stored executions, not a claim that three future draws have guaranteed success or independent errors. It directly demonstrates why comparing a portfolio only with one adapter overstates evidence for its specialized training signal.

The temperature sweep retains all declared conditions instead of selecting the best one for the headline. Through \(T=1.0\) the one-draw rate stays within 41.1--43.1\% on Seen, the three-draw union reaches 60.0/75.2\%, and at \(T=1.5\) the decoder collapses to 15.8/35.2\%. A separate 20-draw stream at \(T=0.8\) reaches 74.8\% Seen and 84.0\% Unseen, using on average 7.44 and 5.08 calls under early stopping. Those higher rates spend a different generation budget and do not replace the three-call primary results. Fine-tuning also matters: the matched base-model three-draw union reaches only 30.4/65.6\%, so adaptation adds 27.2 points [22.99, 31.41] on Seen and 6.4 points [1.19, 11.34] on Unseen. Breadth alone therefore does not explain all improvement over the base model.

At matched temperature, replacing three draws of one checkpoint by one draw from each of three checkpoints changes RR by -0.1 points [-2.00, 1.80] on Seen and 2.4 points [-0.41, 5.31] on Unseen. These intervals do not establish a consistent advantage from checkpoint diversity. They also do not show equivalence: the uncertainty still admits benefits and harms of practical interest. A deterministic multi-seed gain can coexist with this result because sampling from one checkpoint already supplies diversity. The decoder must be controlled before an ensemble result is attributed to independently learned policies.



The current-only factorial in Table~\ref{tab:factorial} tests this explanation on one inference stack. Three greedy checkpoints gain 9.8 [7.85, 11.92] and 10.8 [7.23, 14.64] points over one, but under the matched stochastic decoder distinct checkpoints add only 2.1 points [0.00, 4.16] and 1.2 points [-2.93, 5.93]. The equal-problem Seen interval includes zero, so the rounded instance-weighted lower bound does not establish a robust checkpoint benefit. Absolute greedy-three coverage is 62.9/78.0\% on that stack against 72.0/81.2\% on the historical one. Backend sensitivity is material, and the deployment recommendation is restricted to the evaluated stack rather than asserted as backend-independent superiority.

\noindent\textbf{History and portfolio selection.} Retraining with the same targets but without earlier-submission context yields no significant RR difference in the four principal tests after Holm correction; the smallest adjusted \(p\) is 0.313. This negative result does not localize gains to trajectory-derived relations. At the portfolio level, removing history improves frozen mixed and terminal RR by 8.8/11.1 Seen points and 7.6/6.0 Unseen points, with all intervals excluding zero. The result is compatible with a prompt-distribution cost, especially because terminal training uses single-source inputs. It is inconsistent with describing history as necessary to the measured portfolio advantage. The matched retraining and frozen-input interventions should not be treated as interchangeable estimates.

Selection-space controls also fail to establish a general heterogeneous-target benefit. Answer-9Choose3 receives the same nine-checkpoint pool size and 84-subset opportunity as Mixed. The primary five-fold cross-fitted mixed-minus-terminal contrast is +2.2 points [-0.19, 4.63], compared with the non-cross-fitted +1.7 [-0.79, 4.29]. These estimates are positive but uncertain. Exact replay of the six orders of a fixed triple checks the independent-candidate controller, not the value of learned diversity. There is consequently no basis for turning a verified ordering property or portfolio certificate into a theoretical guarantee about learned repair quality.

\noindent\textbf{Answer to RQ3.} Candidate breadth and adaptation each contribute measured gains. Distinct checkpoints add no consistent advantage once the stochastic decoder is matched, and serialized history is not supported as a necessary input. Target heterogeneity has a small, uncertain unrestricted contrast against the equally searched terminal pool. These controls constrain the mechanism claim rather than merely supplying additional baselines.

\subsection{RQ4: Generality}
\label{sec:generality}
\noindent\textbf{Problems and execution suites.} Within Unseen, Mixed exceeds Zero-shot by 12.8 points [6.83, 18.75], with 45 versus 13 exclusive successes and exact McNemar \(p=3.01\times10^{-5}\). Among 122 joint repairs it reduces TED by 6.41 [3.43, 9.89]. The higher absolute Unseen than Seen RR is not evidence of stronger generalization: the partitions differ in trajectory availability and problem composition. Matching all 54 Unseen problems to distinct Seen problems on six pre-repair difficulty covariates changes the raw gap into -4.6 equal-problem points [-14.18, 5.30]. We therefore rely on within-split paired contrasts, not the direction of the raw cross-split difference. Matching reduces measured imbalance but cannot balance unobserved difficulty.

A complementary observed/hidden-slice check partitions the existing authored suite. On Unseen, Mixed and Answer-9Choose3 jointly pass observed and held-back slices on 189/250 and 184/250 inputs, respectively. Conditional confirmation among observed-suite successes is 189/192 (98.4\%) and 184/186 (98.9\%); 13 versus 8 exclusive joint successes yield \(p=0.383\). Repeating the procedure on all 328 Seen problems with a distinct seed yields 97.8\% and 97.9\% confirmation, but joint success is 452/997 versus 469/997. High confirmation thus does not demonstrate that Mixed wins. These are held-back slices of the same authored tests, not independently authored specifications, and the large conditional percentage must not replace the full-denominator repair rate.

\noindent\textbf{Earlier prefixes.} Across 2,770 Seen and 674 Unseen executable prefixes of eventually successful trajectories, current-only Answer-3Seed reaches 69.6\% and 80.1\% RR. The early, middle, and last thirds reach 70.0\%, 67.6\%, and 71.4\% on Seen and 82.9\%, 77.3\%, and 81.8\% on Unseen. This extends evaluation beyond the last failed submission and finds no simple monotonic position effect. It does not cover trajectories that never reach acceptance, and multiple prefixes from one trajectory are dependent. The 2,770-prefix rate is neither added to the 997-input result nor reported as an independent replication on new users.

\noindent\textbf{Model scale and classroom data.} At 1.5B parameters three checkpoints still gain 13.4 points over one [11.16, 15.92], but mixed-minus-terminal is -0.8 [-2.62, 1.07]. Mixed reaches 50.25\% and the nine-checkpoint terminal control 51.05\% on Seen. This smaller model reproduces the utility of multiple opportunities, not an unrestricted mixed-target advantage. It is one scale change within a model family, not broad model-family coverage. No proprietary frontier model comparison was completed.

The Java portfolio results differ from RQ2's direct matched-target retraining. Mixed-minus-Answer-9Choose3 is positive on four held-out exercises (3.9 points [2.99, 5.11]) and inconclusive on held-out students (0.6 [-1.20, 2.59]). Absolute RR is 56.25\% versus 52.30\% over 304 exercise-held-out trajectories and 83.98\% versus 83.43\% over 181 student-held-out trajectories. The exercise estimate rests on four clusters only: refitting with one exercise left out keeps the contrast between 3.6 and 4.4 points, and single exercises range from 2.5 to 5.5 points. This sensitivity check preserves the sign on those exercises, but four clusters cannot support a broad classroom-population claim. The matched-target tradeoff has clearer cross-population support than a universal portfolio benefit.

\noindent\textbf{Representation and overlap.} Binary accepted/non-accepted mining removes the fine severity ordering but also changes the target set. Retraining changes Progress RR by +2.3 Seen and -2.8 Unseen points in the canonical-minus-alternative direction. The nonuniform changes show that the ordering is not an innocuous implementation detail. Similarly, train/test overlap deserves measurement rather than an assertion of absence. For Mixed and Answer-9Choose3, exact matches between a returned repair and a training-time accepted program occur in 0.6\% and 1.3\% of selections, near-duplicates above a 0.90 token-similarity threshold in 3.8\% and 5.3\%, and median maximum similarity to a same-problem training target is 66.7\% and 68.6\%. Low exact-copy rates do not exclude structural reuse, pretraining contamination, or user-level overlap~\cite{allamanis2019adverse}.

\noindent\textbf{Answer to RQ4.} The matched-target tradeoff replicates on authentic student-held-out Java, and candidate breadth remains useful at smaller model scale. Mixed-target unrestricted superiority does not replicate consistently. Prefix, difficulty, overlap, verdict-order, and hidden-slice checks narrow specific threats without converting CodeNet into a classroom study or test-suite acceptance into semantic correctness.

\subsection{RQ5: Development Diagnosis}
\noindent\textbf{Decision rule.} Subsequent development compared current-only (C), authentic-history (H), shuffled-history (HS), and matched other-user (U) conditions. Adoption required strictly greater pooled stable acceptance for H than every control; no increase versus C in regressions, regression upper bounds, or unknowns; all required problem folds non-worse; and completed evaluation. Regression means losing a previously passed testcase; unknown means unresolved execution. These requirements exceed the fixed-measurement pass-fraction invariant of Algorithm~\ref{alg:generic}. Historical verdicts also differ from replay: only 7,979 of 14,027 unique training targets were cached as accepted. We retain runtime uncertainty rather than interpreting it as learner ability. Detailed audits and predictive studies remain in the artifact; predictive loss is not RR.



\noindent\textbf{History and generation.} Table~\ref{tab:development} preserves all twelve main two-slot modifications. Prompt reordering, full-source histories, and matched fine-tuning fail to distinguish authentic history. A crossed diagnosis gives the H adapter 201 acceptances on current code, 192 on H, 198 on HS, and 206 on U: longer-input adaptation is not an authentic-content benefit. Edit-balanced training produces the highest observed two-slot H rate, 200/320 (62.5\%), but increases regressions (17 versus 15), unknowns (16 versus 15), and regression upper bounds (33 versus 30), with only 3/5 required non-worse folds. H selection misses just seven known accepted candidates; 97 inputs lack a confirmed accepted candidate and 16 remain unresolved. Selection alone cannot eliminate this generation deficit.

Splice output causes 48 format failures, seven resource failures, and 151 valid-to-invalid syntax changes across 640 H attempts. Content anchors reduce representation failures but still yield only 138 acceptances and 26 regressions. Public-feedback and counterexample revision do not pass controls. Hiding failed generated code reduces copying and improves some public-test outcomes, yet final H acceptance remains 190 versus C 204. Likelihood selection then reduces H to 161, with 10 gains and 39 losses; 34 losses select unchanged code. These diagnostics distinguish invalid edits, insufficient candidates, public-test overfitting, and excessive preservation rather than treating every failure as a ranking problem.

\noindent\textbf{Separate eight-draw bank.} An earlier 320-input, 23-problem bank includes 19 initially accepted programs, 288 non-accepted programs, and 13 unknowns; accepted/320 is not failed-input RR. Structural and history-feature refinements reach 203--211 acceptances but fail their original regression and 4/5-fold requirements or match perturbation controls. Conservative preservation reduces regressions but returns unchanged code 155 times, leaving 122 acceptances. Generic public-execution selection is a genuine improvement: C reaches 252/320 (78.75\%), with nine regressions and 13 unknowns, versus the prior selector's 211/320, 51, and 13. It passes its separate 22-check execution-component gate and all five folds. However, H reaches 251/320 with identical regression/unknown counts and does not separate from shuffled controls. Added execution cost and unguaranteed suite independence further prevent ranking this bank against the primary 997/250-input study.

\noindent\textbf{Answer to RQ5.} No completed candidate passes all original history-specific criteria. Earlier pilots and fresh 128-input checks also failed; detailed negative results remain in the final artifact report. The last matched preference run completed 19,199 training and 4,365 validation examples per C/H arm but had no repair inference or testcase evaluation by the cutoff: it has no RR and is not eligible for promotion. We retain the evaluated current-only terminal triple. These adaptively inspected runs diagnose failure modes, not independent confirmatory or educational benefits.

\subsection{Threats to Validity}
\noindent\textbf{Internal validity.} Runtime variability, undefined source ASTs, and Python whitespace affect labels and distances. We retain unknowns, denominators, and whitespace-sensitive corrections; hashes establish provenance, not correctness. Source and peer matching do not equate all target semantics or styles. Prompt-distribution compatibility and inference stacks also affect outcomes, requiring separate within-stack, frozen-input, and matched-retraining contrasts.

\noindent\textbf{Construct validity.} Acceptance is not proof of semantic correctness~\cite{smith2015cure}; same-suite slices are not independent specifications. TED and retention do not measure cognitive load or subsequent learning. CodeNet does not identify novices or measure mastery. Java supplies classroom submissions, not an intervention observing feedback use. Historical verdicts and fresh execution also differ. These distinctions limit educational and target-quality interpretations.

\noindent\textbf{External and conclusion validity.} Filtering favors short, eventually successful Python trajectories and permits Seen user overlap. Java adds one course context and only four held-out exercises. Two scales of one model family do not establish broad generality. Cluster bootstrap and equal-problem estimates do not eliminate small-cluster uncertainty, multiplicity, or adaptive-development bias. Gates were frozen before individual runs, not the entire program; reused development results remain exploratory.

\section{Related Work}
\label{sec:related}
\noindent\textbf{Repair and generation budgets.} Generate-and-validate repair spans search, learned transformations, and language models~\cite{gazzola2019automatic,monperrus2018automatic,weimer2009automatically,legoues2012genprog}. Search analyses~\cite{qi2014strength} and execution-based evaluation~\cite{haque2023fixeval,chen2021evaluating} distinguish candidate quality from exposure. Neural patches, ensembles, synthetic corruption, and execution-informed self-supervision provide different training signals~\cite{tufano2019empirical,lutellier2020coconut,yasunaga2021break,ye2022selfapr}; zero-shot studies examine repair without task adaptation~\cite{xia2022less,jiang2023impact}. Independent ensembles and weight averaging supply other notions of diversity~\cite{lakshminarayanan2017simple,wortsman2022model}. Our adapters execute separately; we do not introduce portfolio repair. We isolate trajectory targets with same-target seeds, equal search spaces, fixed draws, and current-only controls.

\noindent\textbf{Programming-exercise feedback.} Educational repair exploits correct programs through clustering, alignment, and refactoring~\cite{gulwani2018automated,wang2018search,hu2020re}; related representations and tutoring systems propagate feedback and generate hints~\cite{piech2015embeddings,glassman2015overcode,rivers2017datadriven,price2017isnap}. Language models support repair, syntax feedback, conversations, peers, and counterexamples~\cite{joshi2023repair,zhang2024pydex,phung2023generating,liu2024fastfixer,yang2024cref,zhao2024peer,orvalho2025counterexample}. Assignment-aware and diversified feedback use further reference strategies~\cite{heo2023referent,choi2021automated,choi2025automated}. LSGen's iterative edit-driven retrieval~\cite{dai2026learner} retains its strong Seen advantage here. Benchmarking and surveys emphasize population and protocol differences~\cite{yi2017feasibility,koutcheme2024benchmarking,keuning2018systematic}. These methods are not uniformly terminal-target learners. Our narrower intervention replaces the target for matched sources, exposing a coverage--locality tradeoff rather than dominance over all feedback strategies.

\noindent\textbf{History and learner evidence.} ZPD and scaffolding concern supported performance, not program edit distance~\cite{cole1978mind,murray2002toward,chounta2017grey,schulze2024beyond}. Knowledge tracing models proficiency from interactions~\cite{corbett1994knowledge,piech2015deep,ghosh2020context}; TIKTOC incorporates testcase evidence~\cite{duan2024tiktoc}. Next-step hints, feedback ladders, and novice-response studies examine guidance more directly~\cite{roest2024next,heickal2024generating,xiao2024exploring}, while feedback theory emphasizes its interpretation and use~\cite{narciss2008feedback,hattie2007power,shute2008focus,aleven2000limitations}. We test the narrower repair prerequisite: whether authentic history improves generated changes beyond current code and perturbed histories. The results do not establish that prerequisite. Educational claims additionally require comprehension, transfer, and independent-correction measurements, not only executable outputs.

\section{Conclusion}
\label{sec:conclusion}
We presented \textsc{ZPDPatch}, a Mine--Train--Select technique for constructing trajectory-derived repair targets and evaluating execution-guided portfolios. Matched Python and student-held-out Java experiments show a reproducible coverage--locality tradeoff: progress targets preserve more source code on joint successes but repair fewer inputs than terminal targets. Candidate breadth and adaptation explain substantial gains, whereas authentic-history conditioning and target heterogeneity do not establish consistent unrestricted advantages. Completed development improves generic execution selection but supplies no candidate passing all history-specific adoption conditions, so we retain the existing current-only terminal triple rather than promote an unverified revision. Educational benefits and broader model-family generality remain questions for future studies.
