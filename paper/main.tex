\begin{abstract}
We present \tool, a trajectory-supervision approach that constructs repair targets for educational program repair from execution evidence instead of from accepted solutions. Repair systems for programming exercises have markedly improved coverage by aligning correct peer programs or by conditioning language models on the failing submission. However, they all supervise repair toward the terminal program, so a correct repair often replaces most of what the learner wrote, and the effect of the repair target is reported together with the number of generated candidates, which raises coverage on its own. The goal of this paper is to construct repair targets from observed execution evidence, without a repository of correct solutions for the same problem. A key challenge is that the target cannot be varied alone, because changing it also changes the number of training examples, the distribution of failing sources, and the edit distance to the target. To address this, \tool applies a specialized algorithm that iteratively mines three finite improvement relations, matches outcome-equivalent peer targets within distance calipers, and selects a checkpoint triple by exact validation-coverage search, based on data accumulated from re-executed submissions. We evaluate it on 997 Seen and 250 problem-held-out Python inputs and on 181 student-held-out Java trajectories. Under source- and count-matched training, terminal targets repair 19.2 and 11.2 percentage points more inputs, whereas intermediate targets produce repairs that are 10.08 and 6.83 tree-edit units smaller and retain 5.6 and 6.5 more points of the submitted tokens; matched peer targets add 4.3 and 6.0 points, the Java replication reproduces both directions, and three fixed candidate draws alone contribute 15.1 points. End to end, the gated portfolio repairs 61.5\% of Seen inputs, below the 72.0\% of a terminal-target triple and the 80.2\% of retrieval-based generation, so target construction buys locality rather than coverage.
\end{abstract}

\section{Introduction}
\label{sec:introduction}
Automated program repair (APR) for programming education turns a failing submission into a program that passes the exercise tests, giving learners executable, code-specific feedback instead of a coarse verdict~\cite{gazzola2019automatic,monperrus2018automatic,keuning2018systematic}. A repair system generates one or more candidate programs and validates them by execution, returning the candidate that passes the tests~\cite{weimer2009automatically,legoues2012genprog}; systems built for exercises additionally condition generation on the problem statement and the current submission~\cite{joshi2023repair,zhang2024pydex}. Because an exercise is solved by thousands of learners, a repair system can also draw on programs that other learners wrote for the same problem~\cite{gulwani2018automated}.

Educational repair has advanced along two lines. Reference-based systems cluster, align, or normalize correct peer programs and transfer the aligned fragments into the failing program~\cite{gulwani2018automated,wang2018search,hu2020re}. Generation-based systems condition a language model on the failing program and on execution diagnostics, retrieved repair pairs, or an iterative conversation~\cite{joshi2023repair,zhang2024pydex,liu2024fastfixer,yang2024cref,orvalho2025counterexample,dai2026learner}. Both lines have markedly improved repair coverage: in our own setting, the retrieval-based state of the art repairs 80.2\% of failing Python submissions, and a fine-tuned generator repairs 72.0\%.

However, both lines supervise and condition repair toward the same place: the \emph{terminal} program, that is, the accepted solution. In this work, we define a \emph{repair target} as the program that a repair model is trained to produce for a given failing source, and we distinguish \emph{terminal} targets, the first accepted submission of a trajectory, from \emph{intermediate} targets, later submissions that execution evidence shows to be improvements but not yet solutions. Which target is used is an underexplored axis, and it is consequential, because a repair learned toward a terminal target replaces most of what the learner wrote: as shown in Section~\ref{sec:locality}, repairs produced by retrieval-based generation differ from the submitted program by 88.27 abstract syntax tree (AST) nodes on average. The axis is also hard to read off published numbers. In a scoped audit of eight educational repair studies (Section~\ref{sec:limitation}), none isolates the repair target, five deploy or evaluate multiple generation opportunities, and three of those five report no matched single-candidate quantity, so a reported gain can come from extra candidates rather than from supervision.

In this paper, we present \tool, a trajectory-supervision approach that constructs repair targets from execution evidence in submission histories instead of defaulting to the accepted solution, and that does so without a repository of correct same-problem solutions. The core idea is that a learner's own trajectory, and the trajectories of learners whose attempts fail the same tests, already contain programs that are closer to the submitted code than the accepted solution is, and that training on those programs trades coverage for locality in a measurable way.

A key challenge is that the repair target cannot be varied in isolation. The mined relations are not nested and differ in size: our Python corpus yields 40,454 terminal pairs but 21,416 intermediate pairs, so replacing one target rule by another simultaneously changes the number of training examples, the distribution of failing sources, and the edit distance between source and target. Candidate breadth adds a second confound, since one additional generation opportunity raises coverage even when supervision is unchanged. Attributing an effect to target construction therefore requires holding sources, example counts, decoding, candidate budget, and selection fixed at the same time.

To address this challenge, we developed a specialized algorithm that iteratively \emph{mines}, \emph{matches}, and \emph{selects} based on execution evidence accumulated from re-executed submissions. The Mine stage re-executes every submission against the exercise tests and emits three finite improvement relations over the resulting per-test outcome vectors. The Match stage replaces a learner's own intermediate target with another learner's program that has the exact same test outcomes and lies within a token-distance caliper, which fixes the source and the measured target quality while changing only provenance. The Select stage solves checkpoint choice as an exact validation-coverage search and returns a program through an execution gate that admits the unchanged submission as a fallback, so the returned program never lowers the observed pass rate and, under a finite edit budget, never exceeds it.

Experimental results on 997 Seen and 250 problem-held-out Python inputs from Project CodeNet, and on 181 student-held-out Java trajectories from an introductory programming (CS1) course, demonstrate a coverage--locality tradeoff under source- and count-matched training. Terminal targets repair 19.2 and 11.2 percentage points more inputs, whereas intermediate targets produce repairs that are 10.08 and 6.83 AST-edit units smaller and retain 5.6 and 6.5 more source-token points; direct retraining on the student-disjoint Java data replicates both directions (85.6\% versus 50.8\% repair rate, 4.8 more retained token points). Outcome-equivalent peer targets raise intermediate-target coverage by a further 4.3 and 6.0 points. A fixed-decoder contrast attributes 15.1 Seen points to three candidate draws alone, and under a maximum structural edit budget of 20 AST nodes our controller returns an accepted repair for 44.0\% of inputs, compared with 13.9\% for retrieval-based generation.

\noindent\textbf{Contributions.} We summarize our contributions as follows:
\begin{itemize}
  \item \textbf{Underexplored problem:} We identify repair-target construction as an axis that educational repair leaves uncontrolled, show through a scoped audit of eight studies that candidate breadth is reported inconsistently, and quantify the coverage--locality tradeoff under matched training.
  \item \textbf{New technique:} Our core contribution is a specialized algorithm that mines three finite execution-evidence relations from trajectories, substitutes outcome-equivalent peer targets within distance calipers, solves checkpoint selection exactly, and gates candidates to guarantee observed-test non-regression and edit-budget compliance.
  \item \textbf{Extensive evaluation:} We evaluate \tool on two languages, two model scales, and two held-out populations with source-, count-, decoder-, and budget-matched controls, a withheld-test consistency audit, and five-fold problem cross-fitting, and we make the replication package available.
\end{itemize}

\section{Preliminaries}
\label{sec:preliminaries}

\subsection{Trajectory-Supervised Repair}
\label{sec:formulation}
The aim of educational program repair is to turn a failing submission into a program that passes the exercise tests. To do so, a repair system conditions a generator on a learner's observed submissions, generates complete programs, and validates them by execution. For a problem \(p\), we define a submission as a pair \((c,v)\), where \(c\) represents the complete source code and \(v\) denotes the online-judge verdict. A submission trajectory \(\tau=[s_1,s_2,\ldots,s_n]\) is chronologically ordered and terminates at the first accepted submission. The problem context (\(d_p\)) holds the problem statement and the resource limits, and the test suite (\(\mathcal{E}_p\)) holds the available tests. Re-executing a submission yields a per-test outcome vector (\(o\)) that indicates the outcome of every test \(e\in\mathcal{E}_p\), which is strictly more informative than the single verdict \(v\).

A repair example is a pair of an input (\(x\)) and a target (\(y\)), where \(x=(d_p,h)\) consists of the problem context and an observed prefix (\(h\)) of a trajectory, and \(y\) is a complete later program. A \emph{target constructor} (\(T\)) decides which submissions remain in \(h\) and which later submission supplies \(y\); the two need not be adjacent in the original trajectory. Given \(x\), a repair model generates one complete program (\(\hat c\)), which is accepted only after execution.

\begin{algorithm}[h]
\caption{Trajectory-Supervised Program Repair}
\label{alg:generic}
\KwIn{Problem context ($d_p$), trajectories ($H$), tests ($\mathcal{E}_p$), target constructor ($T$), candidate budget ($k$), edit budget ($B$).}
\KwOut{Repaired program ($\hat c$).}
$D \gets \emptyset$\;
\ForEach{$\tau \in H$}{
  \ForEach{failing $c_i \in \tau$}{
    $D \gets D \cup \{((d_p, h_i), T(\tau, i))\}$ \tcp*{$h_i$: observed prefix}
  }
}
$\theta \gets \textsc{FineTune}(D)$\;
$\mathcal{C} \gets \{c\}$ \tcp*{unchanged submission is feasible}
\For{$j \gets 1$ \KwTo $k$}{
  $\mathcal{C} \gets \mathcal{C} \cup \{\textsc{Generate}(\theta, d_p, c)\}$\;
}
\ForEach{$\hat c \in \textsc{Order}(\mathcal{C})$}{
  \If{$\mathrm{Pass}(\hat c) = 1 \wedge \mathrm{ted}(c, \hat c) \leq B$}{
    \Return $\hat c$\;
  }
}
\Return $\arg\max_{\hat c \in \mathcal{C}} (\mathrm{Pass}(\hat c), -\mathrm{ted}(c,\hat c))$\;
\end{algorithm}

Algorithm~\ref{alg:generic} describes a generic trajectory-supervised repair procedure. It takes a problem context (\(d_p\)), trajectories (\(H\)), a test suite (\(\mathcal{E}_p\)), a target constructor (\(T\)), a candidate budget (\(k\)), and an edit budget (\(B\)). For now, let us set aside the last three inputs, which are the subject of this paper; existing systems instantiate \(T\) as terminal closure, fix \(k\) by implementation convenience, and leave \(B=\infty\). At lines 1--5, the procedure pairs every failing submission with the target supplied by \(T\) and fine-tunes a generator on the resulting examples. At line 6, the candidate set is seeded with the unchanged submission, so returning the submission itself always remains possible. Lines 7--8 add up to \(k\) generated programs, and lines 9--11 return the first candidate that passes every test within the edit budget. For simplicity, we omit how outcomes are cached and how candidates are ordered. Finally, line 12 returns the candidate with the highest executed pass rate when no candidate qualifies.

Existing educational repair systems differ in how they fill three places of Algorithm~\ref{alg:generic}. Reference-based systems replace the \textsc{Generate} function at line 8 with alignment against correct peer programs for the same problem~\cite{gulwani2018automated,wang2018search,hu2020re}; language-model systems replace it with conditional generation that is optionally re-invoked with execution diagnostics~\cite{joshi2023repair,zhang2024pydex,liu2024fastfixer,yang2024cref,orvalho2025counterexample}; retrieval-based generation additionally supplies historical repair pairs written by other learners~\cite{dai2026learner}. The constructor \(T\) at line 4, however, is effectively the same in all of them: each failing submission is paired with an accepted solution, and the edit budget remains infinite.

\subsection{Limitation of Terminal-Target Supervision}
\label{sec:limitation}

Our key observation is that \(T\) is not treated as a design choice, even though a trajectory contains programs other than the accepted one. In this work, we define an \emph{intermediate target} as a later submission of the same trajectory that improves on the current submission under observed execution evidence but is itself not accepted. More precisely, a later submission \(s_t\) is \emph{reachable} from \(s_r\) when it occurs in the same learner's trajectory and either its verdict is strictly better, or the two verdicts are equal while \(o_t\) is no worse than \(o_r\) on every test and strictly better on at least one. Reachability is an empirical property of the observed snapshot; it implies neither minimality nor educational value.

Suppose a learner submits a program that fails six of ten tests, then a revision that fails two of those six, and finally an accepted program. Terminal closure pairs the first program with the accepted one and discards the revision. In this case, we classify the revision as an intermediate target of the first program: it is reachable under the evidence order above, and it stays closer to what the learner actually wrote.

Terminal supervision carries a measurable cost in how much of the submission survives a repair. As shown in Section~\ref{sec:locality}, repairs returned by retrieval-based generation differ from the submitted program by 88.27 AST nodes on average and those returned by an execution-aware zero-shot baseline by 27.25; under a maximum structural edit budget of 20 AST nodes, retrieval-based generation returns an accepted repair for only 13.9\% of inputs. The cost is also hard to read off published results, because the number of generated candidates is reported inconsistently. Table~\ref{tab:breadth-audit} codes eight directly related neural and language-model educational-repair studies using a rule frozen before our extended breadth results. Five deploy or primarily evaluate multiple generated opportunities. Only the EPR benchmark reports pass@1/5/10, while CREF exposes AVG-5 beside TOP-5; PyDex, counterexample-guided repair, and LSGen do not isolate extra opportunities with a matched one-candidate control~\cite{zhang2024pydex,koutcheme2024benchmarking,yang2024cref,orvalho2025counterexample,dai2026learner}. Adaptive iterations can carry new evidence, so this observation motivates explicit candidate accounting rather than invalidating those methods.

This purposive audit covers only eight studies. Its reporting contract requires same-decoder one-draw repair rate, union coverage at each deployed $k$, a fixed selection rule, and calls with explicit timing units. Section~\ref{sec:breadth} supplies these quantities. Our non-adaptive candidates permit exact replay; adaptive feedback methods can change the candidate distribution and require different accounting.

One alternative is to mine every later submission as a target. However, this naive constructor changes more than the target: the mined relations are not nested and differ in size, yielding 40,454 terminal and 21,416 intermediate training pairs in our Python corpus, so example counts and the distribution of failing sources move together with the target. A second alternative is to leave \(T\) unchanged and raise the candidate budget \(k\) instead. As shown in Section~\ref{sec:breadth}, three fixed stochastic draws alone contribute 15.1 repair-rate points on Seen inputs, which exceeds most target effects reported in this paper, so an uncontrolled budget can hide or manufacture an apparent target effect.

\noindent\textbf{Goal.} These observations motivate a target constructor that is mined from finite execution evidence and evaluated under matched conditions. We call a constructor successful when it preserves more of the submitted program at equal coverage, or raises coverage at equal preservation, under a stated edit budget. Our work thus tackles two challenges: (1) instantiating \(T\) from auditable per-test evidence rather than from assumed pedagogical value, and (2) separating the effect of \(T\) from the candidate budget (\(k\)), the number of training examples, and the checkpoint pool, each of which changes coverage on its own.

\section{Our Approach}
\begin{algorithm}[h]
\caption{\tool}
\label{alg:tool}
\KwIn{Problem context ($d_p$), trajectories ($H$), tests ($\mathcal{E}_p$), donor pool ($\mathcal{P}$), current submission ($c$), candidate budget ($k$), edit budget ($B$).}
\KwOut{Repaired program ($\hat c$).}
\tcc{Step 1. Mine stage}
$D \gets \emptyset$\;
\ForEach{$\tau \in H$}{
  $O \gets \textsc{Execute}(\tau, \mathcal{E}_p)$ \tcp*{cached per-test outcomes}
  \ForEach{relation $\rho \in \{\progress, \strict, \answer\}$}{
    $D \gets D \cup \textsc{Mine}(\tau, O, \rho)$\;
  }
}
\tcc{Step 2. Match stage}
$D_m \gets \textsc{Match}(D, \mathcal{P})$ \tcp*{outcome-equivalent peer targets}
\tcc{Step 3. Select stage}
$V \gets \{\textsc{FineTune}(D_m, \rho, \sigma) \mid \rho \in \{\progress,\strict,\answer\},\ \sigma \in \mathit{Seeds}\}$\;
$S \gets \arg\max_{S' \subseteq V,\ |S'| = k} f_B(S')$ \tcp*{exact validation search}
\tcc{Inference}
$\mathcal{C} \gets \{c\} \cup \{\textsc{Generate}(v, d_p, c) \mid v \in S\}$\;
\Return $\textsc{Gate}(\mathcal{C}, B)$ \tcp*{lines 9--12 of Algorithm~\ref{alg:generic}}\;
\end{algorithm}

\label{sec:approach}

\subsection{Overview}
Figure~\ref{fig:overview} shows how \tool constructs repair targets while interacting with a generator and an execution environment. \tool operates in three stages: Mine, Match, and Select. Initially, in the Mine stage, every submission of every trajectory is re-executed against the exercise tests, and three finite relations over the resulting per-test outcome vectors emit (prefix, target) pairs: \progress mines verdict improvements and same-verdict per-test improvements, \strict requires a strictly better verdict, and \answer pairs each failure with the first accepted submission. In the Match stage, a mined target may be replaced by another learner's program that has the exact same test outcomes and lies within a token-distance caliper, which changes provenance while holding the source and the measured target quality fixed. In the Select stage, one checkpoint is fine-tuned per relation and seed, an exact search returns the triple with the best validation coverage under an optional edit budget, and inference executes the resulting candidates behind a non-regressive gate. The key novelty of \tool lies in the Mine and Match stages: the straightforward alternative of pairing every failure with the accepted solution is exactly the terminal constructor whose coverage--locality cost we measure in Section~\ref{sec:target}. A typical usage scenario runs the three offline stages once per corpus and then serves repairs with the three frozen checkpoints.

\subsection{\tool}
Algorithm~\ref{alg:tool} details how \tool instantiates the constructor (\(T\)), the candidate budget (\(k\)), and the gate that Algorithm~\ref{alg:generic} leaves open. It accepts the problem context (\(d_p\)), the trajectories (\(H\)), the tests (\(\mathcal{E}_p\)), a donor pool (\(\mathcal{P}\)) of other learners' submissions, the current submission (\(c\)), the candidate budget (\(k\)), and an edit budget (\(B\)); no user-supplied seed corpus, reference solution, or parameter space is required. \textsc{Gate} denotes the ordered scan and fallback of lines 9--12 of Algorithm~\ref{alg:generic}. At lines 1--5, the Mine stage re-executes each trajectory once, caches the per-test outcome vectors, and emits the relation-specific pairs. At line 6, the Match stage rewrites the target of a mined pair whenever an eligible peer target exists. At lines 7--8, the Select stage fine-tunes one checkpoint per relation and seed and searches all triples for maximum validation coverage; the selected triple (\(S\)) is then frozen. At inference, lines 9--10 generate at most one candidate per selected checkpoint and return the gated choice, so the deployed call budget equals \(|S|\) and never grows with the corpus. We set the candidate budget to \(k=3\), so the selected portfolio holds three checkpoints, and train three seeds per relation, giving nine candidates; both values were fixed by trial and error on validation coverage alone, and Section~\ref{sec:breadth} reports what the same budget buys without relation-mined targets.

\subsection{Mine Stage}
The goal of the Mine stage is to emit (prefix, target) pairs whose targets are justified by observed execution evidence rather than by assumed pedagogical value (lines 1--5). To do so, we group submissions by problem and learner, sort them by time, and stop at the first acceptance. After indentation, comment, and blank-line normalization we remove only consecutive duplicates, so a learner who returns to an earlier idea still contributes evidence of a distinct attempt. Complete source, verdict, and order are preserved, with no maximum history or transition count. Every state is re-executed, and cache keys bind problem, normalized code, test-suite identity, timeout, and memory limit, which prevents incompatible reuse across configurations. Runner failures receive an explicit most-severe outcome, and Mine requires a complete outcome vector before emitting a pair.

To order evidence, we assign severity 0 to accepted (\texttt{AC}), 1 to wrong answer (\texttt{WA}), 2 to time- and memory-limit exceeded (\texttt{TLE}, \texttt{MLE}), 3 to runtime error (\texttt{RE}), 4 to compile error (\texttt{CE}), and 5 to internal failures. This operational preorder mines labels; it does not claim that every \texttt{WA} program is semantically closer to correctness than every \texttt{RE} program. For equal, non-empty test keys, \(o_t\preceq_{\mathrm{sev}}o_r\) holds iff no outcome in \(o_t\) is more severe than its counterpart in \(o_r\). Test-case progress is then the Pareto condition
\begin{equation}
\mathrm{TCProg}(r,t)=
\mathbf{1}\!\left[o_t\preceq_{\mathrm{sev}}o_r \land o_t\neq o_r\right].
\label{eq:tcprogress}
\end{equation}
Intuitively, \(\mathrm{TCProg}\) fires exactly when a revision fixes at least one test without breaking another, which is invisible to the coarse verdict.

The three relations differ in which later submission they retain. \answer applies terminal closure: if \(s_n\) is accepted, every preceding non-accepted submission is independently paired with \(c_n\), so for \(\tau=[s_1,\ldots,s_9]\) the rule produces \(([s_1],c_9),\ldots,([s_8],c_9)\) and no multi-submission history. \strict keeps a retained scan: starting with \(R=[s_1]\), it appends \(s_t\) only when \(\mathrm{sev}(v_t)<\mathrm{sev}(v_r)\) for the last retained submission \(s_r=R[-1]\), and emits \(([r_1,\ldots,r_{j-1}],c_{r_j})\) for every \(j=2,\ldots,m\), where \(m\) is the number of retained submissions; the comparison is against the last retained state, not necessarily the immediately preceding submission. \progress uses the same scan but also appends \(s_t\) when \(v_t=v_r\) and Equation~\eqref{eq:tcprogress} holds, so it captures monotone per-test progress that an unchanged verdict hides. Formally, writing \(s\prec_S t\) when \(\mathrm{sev}(v(t))<\mathrm{sev}(v(s))\),
\[
s\prec_P t \iff s\prec_S t\ \lor\
\left(v(s)=v(t)\land o(t)\prec_{\times}o(s)\right),
\]
where the strict product order \(\prec_{\times}\) requires every test to be no worse and at least one to be better. Thus \(\prec_S\subseteq\prec_P\) as pairwise relations, although the edge sets emitted by independent retained scans need not be nested.

For example, consider a trajectory \texttt{WA} \(\to\) improved \texttt{WA} \(\to\) \texttt{AC}. \answer connects both failures directly to the accepted program, \strict connects the first state to the accepted one because the intermediate verdict is unchanged, and \progress emits the two intervening edges. Both scans are acyclic, because each edge lexicographically decreases verdict severity and summed test severity. The guarantee concerns mined labels only: incomplete outcome vectors fail closed, and generated programs still require execution.

The severity order is a design choice, so we audited it rather than assuming it. Collapsing it to a binary accepted/non-accepted criterion mines 14,027 of 16,973 \strict and 18,009 of 21,416 \progress pairs, that is 82.6\% and 84.1\% of the canonical labels, and 100\% and 98.6\% of those binary pairs remain valid when \texttt{RE} is placed below \texttt{WA}. Models retrained on them agree with the canonical ones on 84.6\% and 87.5\% of Seen repair decisions (Section~\ref{sec:generality}), so we read the ranking as operational rather than universal.

\subsection{Match Stage}
The goal of the Match stage is to vary where a target comes from while holding what the target achieves fixed (line 6). Same-trajectory reachability is only one way to instantiate an intermediate target: another learner who failed the same tests may have written a program that is equally close to the current submission. For current code \(c\), same-user target \(y_u\), token edit distance \(d\), and execution vector \(o\), an eligible peer \(y_v\) must belong to another learner on the same problem and satisfy
\[
o(y_v)=o(y_u) \ \wedge\ \left(\delta\le2 \ \vee\ \delta/\max(1,d(c,y_u))\le0.1\right),
\]
where \(\delta=|d(c,y_v)-d(c,y_u)|\) and the disjunction applies only to the distance caliper, never to the outcome equality. Intuitively, the peer target must be indistinguishable from the same-user target in what the tests report and in how far it sits from the submitted program, so a difference in repair behavior can be attributed to provenance rather than to target quality or edit size.

Matching greedily visits scarce evidence groups first and minimizes distance discrepancy, then donor reuse and identifier, subject to a reuse cap of three; it is not a global minimum-cost matching, and we report the resulting donor distribution instead of claiming optimality. The construction is deliberately conservative: only 24.4\% of mined \progress training records and 11.4\% of validation records admit an eligible peer, so the matched population is a selected subset that we define explicitly rather than a corpus-wide replacement. Donors are drawn only from the same split as the recipient, which keeps validation targets out of training. Empirically, the substitution raises intermediate-target coverage by 4.3 and 6.0 points, as shown in Section~\ref{sec:target}.

\subsection{Select Stage}
The goal of the Select stage is to turn independently trained checkpoints into a small deployed portfolio and to return a program that cannot be worse than the submission (lines 7--10). All checkpoints share one role-neutral prompt containing the statement, the limits, the stored submissions with execution and edit summaries, and a request for a complete solution; no policy name or edit-size instruction is supplied, and independent QLoRA adapters minimize cross entropy on assistant target tokens only.

Training loss does not measure repair complementarity, so selection is driven by executed validation repairs. Let \(V=V_P\mathbin{\dot\cup}V_S\mathbin{\dot\cup}V_A\) collect the checkpoints trained on \progress, \strict, and \answer, let \(U\) be the validation instances, and let \(R_v\subseteq U\) be those repaired by checkpoint \(v\). We maximize
\[
 f(S)=\Bigl|\bigcup_{v\in S}R_v\Bigr|\Big/|U|.
\]
Intuitively, \(f\) rewards checkpoints that repair different instances rather than the same ones, which training loss cannot distinguish. We exhaustively search all \(\binom{9}{3}=84\) triples, of which 27 take one checkpoint per relation, on one fixed-hash trajectory from each of 461 validation problems, so the reported triple is the exact maximizer rather than a heuristic choice. For \(\mathcal B=\{5,10,20,40,80,160\}\), the budget-indexed variant \(R_v^B\) retains only repairs whose edit distance is at most \(B\), and we maximize either \(f_B\) or its mean over \(\mathcal B\). Test outcomes never enter selection.

At inference, the selected checkpoints receive the same observed input and independently emit one program each; candidates never enter another checkpoint's prompt, so the portfolio is non-adaptive and exactly replayable. For a budget \(B\in[0,\infty]\), the feasible set is
\begin{equation}
\mathcal{C}_B=\begin{cases}
\{c_i\}\cup\{c^{(j)}\}_{j=1}^{k}, & B=\infty,\\
\{c_i\}\cup\{c^{(j)}:\mathrm{ted}^{\dagger}(c_i,c^{(j)})\leq B\}, & B<\infty,
\end{cases}
\label{eq:feasible-set}
\end{equation}
where \(\mathrm{ted}^{\dagger}(c_i,c)=0\) for the unchanged fallback, the abstract syntax tree (AST) tree edit distance (TED) when both changed programs parse, and \(+\infty\) otherwise. A finite budget therefore rejects changed candidates when the submission does not parse, whereas unrestricted operation imposes no distance gate and can repair syntactically invalid input. The scan stops at the first accepted candidate in \(\mathcal{C}_B\); if none is accepted, selection is lexicographic,
\begin{equation}
c^*=\underset{c\in\mathcal{C}_B}{\arg\max}
\left(\mathrm{Pass}(c),-\mathrm{ted}^{\dagger}(c_i,c)\right),
\label{eq:selection}
\end{equation}
which maximizes executed correctness and then minimizes change. Because the unchanged submission is always feasible, three properties follow directly from Equations~\eqref{eq:feasible-set} and~\eqref{eq:selection}: selection never lowers the observed pass rate, every returned change has defined edit distance at most \(B\), and the exhaustive scan returns an eligible acceptance whenever one is emitted, so candidate order affects calls and patch identity but not fixed-set coverage. When no candidate improves the submission, the zero-distance fallback makes the system abstain instead of returning a regression. These properties constrain the controller, not the learned behavior or hidden-test correctness.

Mining costs \(O(n|\mathcal{E}_p|)\) time and \(O(n)\) storage for a trajectory of \(n\) submissions, and terminal closure costs \(O(n)\). Replaying the deployed portfolio sums generation and candidate execution to 13.62 seconds per input, against 24.40 for retrieval-based generation, excluding cached input execution; nine 155MB adapters occupy 1.4GB. In this manner, without a same-problem solution repository, \tool mines, matches, and selects repair targets from execution evidence accumulated over observed trajectories, and returns a gated program whose edit size the deployer bounds.

\section{Experiments}
\label{sec:experiment}
In this section, we experimentally evaluate \tool to answer the following four research questions:

\begin{itemize}
  \item \textbf{Target construction}: How does the repair target affect repair coverage and the amount of the submitted program that survives?
  \item \textbf{Repair locality}: How does the gated controller compare with zero-shot and retrieval-based repair, with and without an edit budget?
  \item \textbf{Component efficacy}: How much coverage comes from relation-mined targets, trajectory conditioning, candidate draws, and checkpoint identity?
  \item \textbf{Generality}: Do the findings hold on held-out problems and learners, a smaller model, and a second language?
\end{itemize}

We implemented \tool on Qwen2.5-Coder-7B-Instruct~\cite{hui2024qwen2}, a widely used open-weight code model, training one 4-bit QLoRA adapter~\cite{dettmers2023qlora} per relation and seed. All experiments were conducted on a single NVIDIA RTX 5090, and every candidate was executed in a network-disabled container that runs Python and compiles Java 21.

\noindent\textbf{Benchmarks.} We build the primary corpus from Project CodeNet's Python800 benchmark~\cite{puri2021project}. We retain trajectories with at least three submissions, at least one non-accepted state before the first acceptance, and a final accepted program present in the benchmark reference set; we remove post-acceptance submissions and consecutive normalized duplicates, and require every learner to appear in at least three problems and every retained problem to contain at least two trajectories. The refined corpus contains 546 problems, 21,454 trajectories, 99,432 submissions, and 10,088 tests. Before splitting, we tokenize every possible prompt--target configuration and exclude an entire trajectory when any configuration exceeds 4,096 tokens, which removes 3,660 trajectories and leaves 17,794; no later truncation of code, history, or tests is applied. We sort problems by eligible trajectory count, assign the top 90\% (492 problems) to \emph{Seen} and the remaining 54 low-resource problems to \emph{Unseen}, and split Seen trajectories 80:10:10 within each problem (Table~\ref{tab:data}). Evaluation uses the last non-accepted submission before the recorded acceptance, A test trajectory contributes an instance only when it passes both execution checks on re-execution, which reduces the 1,754 Seen and 259 Unseen test trajectories to 997 Seen instances from 328 of the 492 Seen problems and 250 Unseen instances from all 54 held-out problems; the remaining Seen problems still contribute training or validation trajectories. The estimand is therefore conditional repair of the last failed state of an eventually successful trajectory. Because CodeNet identifies online-judge users rather than enrolled students, we add a course corpus: TIKTOC supplies tests for authentic CS1 Java CodeWorkout submissions~\cite{duan2024tiktoc}, and the same construction, split by student, yields 1,125 trajectories from 224 students over 17 exercises, of which 181 trajectories from 33 held-out students form the Java test set. A second CodeWorkout split holds out exercises instead of students, with 10 training, 3 validation, and 4 test exercises (605, 216, and 304 trajectories); Section~\ref{sec:generality} uses it for the exercise-held-out contrast.

\noindent\textbf{Baselines.} We compare \tool with three baselines and one naive variant. \emph{Zero-shot} is an execution-aware iterative baseline that uses the same base model and prompt without fine-tuning and, after a failure, appends the verdict and the number of passed tests before its next call. \emph{Answer-3Seed} is the naive terminal constructor of Section~\ref{sec:limitation}: three adapters trained on the 40,454 terminal pairs with identical model, hyperparameters, decoder, and call budget, varying only the seed. We report it under two prompt variants: \emph{history} serializes the observed prefix, while \emph{current} shows only the failing submission; \emph{Answer-1 (current)} is the single-checkpoint version of the latter. \emph{Answer-9Choose3} is the strictest comparison, because it trains nine terminal checkpoints and receives the same exhaustive 84-triple validation search as the mixed pool, matching prompts, decoding, pool size, and selection opportunity. \emph{LSGen} is a retrieval-based solution generator~\cite{dai2026learner}; we preserve its repair-pair filtering, edit-vector retrieval, diff-guided generation, and re-retrieval, and replay the same edit gate. Since LSGen retains other learners' Seen-Train solutions for the target problem, Unseen evaluation would expose same-problem correct programs, so we omit it there rather than supply unavailable references.

\noindent\textbf{Other settings.} All approaches share the base model, public tests, a 2.5-second per-test timeout, a 2GB memory limit, at most three candidate generations, and a 4,096-token generation cap. Seeds 2027--2029 are repeated for every target, and Answer-9Choose3 adds seeds 2030--2035 without changing data or decoding. Pass Rate (PR) averages the test pass fraction of the returned program, Repair Rate (RR) averages whether it passes every test, and Improvement Rate (IR) averages whether it improves on the submission; Tree edit distance is reported in two directions on parseable repairs~\cite{zhang1989simple,pawlik2016tree}: \(\mathrm{TED}_{B\rightarrow F}\) is the distance from the submitted buggy program to the returned fixed one, and \(\mathrm{TED}_{F\rightarrow O}\) the distance from the returned program to the accepted program recorded later in the same trajectory, which serves as the oracle. Retention measures the fraction of submitted tokens or non-empty lines that survive. We report Wilson intervals~\cite{wilson1927probable}, exact McNemar tests~\cite{mcnemar1947note}, and Holm correction within comparison families~\cite{holm1979simple}; primary paired intervals resample problems 10,000 times with recorded seeds, and Java reports both student- and exercise-cluster intervals~\cite{efron1979bootstrap}. Endpoints, folds, selectors, budgets, and bootstrap draws were fixed before test generation, and final-test outcomes never enter training or selection, although no protocol was externally preregistered.
\subsection{RQ1: Target Construction}
\label{sec:target}

Table~\ref{tab:paired-target} shows that the repair target moves coverage and locality in opposite directions. The paired-target control inner-joins intermediate and terminal examples by problem, learner, submission identifier, and exact current code, discards pairs with the same target, and serializes only the shared current code, so 7,389 training and 931 validation pairs fix the sources, counts, seeds, prompts, selectors, and test inputs; only the target differs. Under this control, intermediate targets lose 19.2 Seen and 11.2 Unseen RR points, both clustered intervals exclude zero, and exact McNemar tests give \(p=7.85\times10^{-34}\) and \(p=6.17\times10^{-5}\). The same control confirms the opposite direction for locality: on 278 and 134 jointly repaired parseable instances, terminal patches are 10.08 units larger [7.53, 12.99] on Seen and 6.83 units larger [4.58, 9.39] on Unseen, and across 299 and 154 joint repairs intermediate targets retain 5.6 and 6.5 more token points and 8.9 and 10.4 more line points, with every clustered interval excluding zero. Exceptionally, 21 Seen and 20 Unseen joint repairs start from syntactically invalid source code, so both returned repairs parse but their AST distance is undefined; those instances contribute to coverage and lexical retention only.

Provenance is a second lever on the same stage. Replacing each same-user intermediate target with an outcome-equivalent peer target raises coverage from 50.4\% to 54.7\% on Seen and from 78.4\% to 84.4\% on Unseen, that is, by 4.3 points [-7.71, -0.84] and 6.0 points [-11.79, -0.41] in the paired same-minus-peer direction, with exact McNemar \(p=0.005\) and \(p=0.032\). Direct retraining on the Java corpus replicates the tradeoff outside CodeNet and without student overlap. On 181 student-held-out trajectories, terminal targets repair 155 trajectories and intermediate targets 92, a difference of 34.8 points with student-cluster interval [-44.91, -25.47] and exercise-cluster interval [-47.31, -23.79]; of 90 joint repairs, intermediate targets retain 4.8 more lexical-token points and 5.1 more line points. These results indicate that terminal targets maximize coverage while intermediate targets maximize source preservation, and that the direction of both effects survives a change of language, population, and course setting.

\subsection{RQ2: Repair Locality and Edit Budget}
\label{sec:locality}

Table~\ref{tab:main-results} shows that the execution-gated portfolio repairs 613 of 997 Seen programs (61.5\%) against 306 (30.7\%) for Zero-shot, with Wilson intervals [58.43, 64.46] and [27.91, 33.62]. The paired gain of 30.8 points holds under problem-cluster bootstrap [26.43, 35.09] and remains 26.1 points [21.24, 30.93] when problems are weighted equally; PR rises by 11.1 points [9.16, 13.02] and IR by 25.2 points [20.83, 29.37]. The two systems are complementary rather than nested: 342 instances are repaired only by \tool and 35 only by Zero-shot (exact McNemar \(p<10^{-63}\)). Notably, the strongest learned configuration in this stack is the current-only terminal triple at 72.0\% Seen and 81.2\% Unseen, which we therefore report as the unrestricted deployment default.

Interestingly, retrieval-based LSGen achieves the highest unrestricted coverage of all systems, with 88.0\% PR, 80.2\% RR, and 82.4\% IR; it repairs 267 instances that \tool misses while \tool repairs 80 that it misses (\(p<10^{-23}\)), and the clustered RR difference is \(-18.8\) points [-23.04, -14.46]. The difference is paid in patch size. Mean \(\mathrm{TED}_{B\rightarrow F}\) is 21.05 for \tool against 27.25 for Zero-shot and 88.27 for LSGen, and on jointly repaired instances \tool reduces distance by 8.46 units [5.05, 12.55] and 43.34 units [38.47, 48.44], so the comparison is not confounded by different success sets.

Figure~\ref{fig:budget} operationalizes that tradeoff under a deployment gate. At a maximum structural edit budget of 20 AST nodes, the gate returns an accepted repair for 44.0\% of inputs with \tool against 13.9\% with always-three LSGen, a problem-clustered difference of 30.1 points [26.45, 33.82]; across the six predeclared budgets the mean difference is 14.7 points [12.03, 17.43]. LSGen crosses over only at the broadest budget, where it leads by 9.7 points. The relation-level ordering agrees: giving each adapter a single candidate on the same 997 instances, terminal supervision reaches the highest RR but the largest mean patch (TED 20.22), while intermediate supervision gives up 5.2 RR points [2.47, 7.91] for the smallest patch (TED 15.85); on 350 joint repairs the paired difference is 1.84 units [0.50, 3.26], although the median gap across 341 compact joint repairs is zero, so the effect lives in the tail. These results indicate that retrieval wins unrestricted coverage whereas the gated portfolio covers more inputs whenever large structural replacement is disallowed. We treat edit distance only as an explicit change-cost axis: the benchmark supplies no evidence that a particular budget is an educational requirement.

\subsection{RQ3: Component Efficacy and Candidate Breadth}
\label{sec:breadth}

For fixed candidates over \(N\) evaluation instances, let \(Z_{ij}\) indicate that draw \(j\) repairs instance \(i\) and \(M_i=\sum_{j=1}^k Z_{ij}\). The realized contribution of breadth alone is exactly

\begin{equation}
 \widehat\Delta_{\mathrm{breadth}}
 =\frac{1}{N}\sum_i\left[\mathbf{1}(M_i>0)-\frac{M_i}{k}\right]\geq0,
 \label{eq:breadth-decomposition}
\end{equation}

which is positive exactly when success differs across draws and therefore cannot be attributed to temperature. Figure~\ref{fig:breadth} applies Equation~\eqref{eq:breadth-decomposition} under a fixed stochastic decoder. Replacing greedy decoding by one stochastic draw costs 7.6 points [-9.81, -5.41], whereas execution-selecting three of those identical fixed draws contributes 15.1 points [13.48, 16.76]. Through \(T=1.0\) the one-draw rate stays within 41.1--43.1\% on Seen, the three-draw union reaches 60.0/75.2\%, and at \(T=1.5\) the decoder collapses to 15.8/35.2\%. Extending the same candidate stream raises coverage monotonically to 74.8/84.0\% at 20 draws, at 7.44/5.08 mean calls. Fine-tuning contributes a second, larger effect: the matched base-model three-draw union reaches only 30.4/65.6\%, so adaptation adds 27.2 points [22.99, 31.41] on Seen and 6.4 points [1.19, 11.34] on Unseen.

Checkpoint identity, by contrast, adds no conclusive third effect. At matched temperature, replacing three draws of one checkpoint by one draw from each of three checkpoints changes RR by \(-0.1\) points [-2.00, 1.80] on Seen and 2.4 points [-0.41, 5.31] on Unseen. A current-only four-cell comparison on a single inference stack agrees: three greedy checkpoints gain 9.8 [7.85, 11.92] and 10.8 [7.23, 14.64] points over one, but under the matched stochastic decoder distinct checkpoints add only 2.1 points [0.00, 4.16] and 1.2 points [-2.93, 5.93]. Absolute greedy-three coverage is 62.9/78.0\% on that stack against 72.0/81.2\% on the historical one, so stack sensitivity is material and no backend-independent deployment advantage follows.

Enlarging the pool or mixing relations does not raise coverage either. Growing the terminal pool from three to nine checkpoints changes RR by \(-1.9\) points [-4.30, 0.32]; the primary five-fold cross-fitted mixed-minus-terminal contrast is \(+2.2\) points [-0.19, 4.63] and the non-cross-fitted estimate \(+1.7\) [-0.79, 4.29]. Across six budgets the mixed pool improves mean Seen RR by 1.2 points [0.02, 2.42], but the Unseen interval includes zero, the 1.5B replication reverses sign, and the user-held-out Java interval includes zero, so we reject a general mixed-target coverage claim and retain source preservation as the supported specialization: on 532 joint repairs the mixed pool preserves 2.6 more token points [1.56, 3.64] and 3.3 more line points [1.89, 4.83]. Trajectory conditioning behaves the same way. Matched retraining that removes only the earlier submissions yields no stable serialization effect, and none of the four RR contrasts survives Holm correction (minimum adjusted \(p=.313\)); at the portfolio level, removing history instead improves frozen mixed and terminal RR by 8.8/11.1 Seen points and 7.6/6.0 Unseen points, with all intervals excluding zero. These results indicate that candidate breadth and fine-tuning account for most of the coverage, whereas checkpoint identity, pool size, and serialized history do not.

\subsection{RQ4: Generality and Replication}
\label{sec:generality}

On the 250 problem-held-out Unseen instances, \tool reaches 74.8\% RR against 62.0\% for Zero-shot, a paired gain of 12.8 points [6.83, 18.75] with 45 versus 13 exclusive repairs (\(p=3.01\times10^{-5}\)), and its patches are 6.41 AST-edit units smaller on 122 joint parseable repairs [3.43, 9.89]. Because trajectory availability rather than randomized difficulty defines the split, the higher absolute rate does not mean that unseen problems are easier: a pre-repair audit that matches all 54 Unseen problems to distinct Seen problems on six outcome-free difficulty covariates turns the raw gap into \(-4.6\) problem-balanced points [-14.18, 5.30], which is why we rely on within-split paired contrasts.

A withheld-test audit separates candidate selection from success assessment. It splits the tests of each problem by fixed hashes, recomputes prompts and selection from the observed side alone, and scores the returned repairs on the hidden side. Under this protocol, 189 of 192 \tool repairs and 184 of 186 matched repairs also pass every hidden test, giving joint RR 75.6\% versus 73.6\% with 13 versus eight exclusive repairs (\(p=.383\)) and confirmation rates of 98.4\% and 98.9\%; repeating the procedure on all 328 Seen problems with a distinct seed yields 97.8\% and 97.9\% confirmation. Both slices come from one authored suite, so they bound slice overfitting rather than establishing semantic correctness. The conventional endpoint is also not load-bearing: across 2,770 Seen and 674 Unseen executable prefixes of eventually successful trajectories, the deployed configuration reaches 69.6\% and 80.1\% RR, and the early, middle, and last thirds reach 70.0\%, 67.6\%, and 71.4\% on Seen and 82.9\%, 77.3\%, and 81.8\% on Unseen.

Finally, the portfolio findings are stable under scale and protocol perturbations, while the mixed-pool advantage is not. At 1.5B parameters three checkpoints still gain 13.4 points over one [11.16, 15.92], but mixed-minus-terminal is \(-0.8\) [-2.62, 1.07]; on Java the same contrast is positive on four held-out exercises (3.9 points [2.99, 5.11]) and inconclusive on held-out students (0.6 [-1.20, 2.59]). The exercise estimate rests on four clusters only: refitting with one exercise left out keeps the contrast between 3.6 and 4.4 points, and single exercises range from 2.5 to 5.5 points; retraining both relations under the binary verdict order changes intermediate-target RR by 2.3 and \(-2.8\) points. Exact matches between a returned repair and a training-time accepted program occur in 0.6\% and 1.3\% of selections, near-duplicates above a 0.90 token-similarity threshold in 3.8\% and 5.3\%, and the median maximum similarity to any same-problem training target is 66.7\% and 68.6\%, so non-exact reuse is bounded rather than excluded. These results indicate that the target-construction tradeoff and the controller guarantees transfer across problems, learners, scales, and languages, whereas a general mixed-pool coverage advantage does not.

\subsection{Threats to Validity}
\label{sec:threats}

(1) \emph{Construct.} Test passing is not semantic equivalence, and edit distance and retention measure change rather than pedagogy; we therefore report them as change costs only, and the withheld-test audit confirms 98.4\% and 98.9\% of repairs on untouched tests. (2) \emph{Internal.} The paired controls fix sources and counts, and peer matching additionally fixes target outcomes within token-distance calipers, but not all structural or stylistic properties; no protocol was externally preregistered, and the artifact records every declared amendment. (3) \emph{External.} Evidence covers one Python benchmark and model family, one smaller model, and two Java splits; Seen permits problem and user overlap, audits cannot eliminate memorization~\cite{allamanis2019adverse}, all-prefix evaluation includes only eventually successful trajectories, and CodeNet is not a classroom cohort, so learner utility remains unmeasured.

\section{Related Work}
\label{sec:related}
\noindent\textbf{Repairing student programs.} Our work shares a common goal with systems that turn a failing student submission into a program that passes the exercise tests~\cite{gulwani2018automated,wang2018search,hu2020re,joshi2023repair,zhang2024pydex,liu2024fastfixer,dai2026learner}. Reference-based systems cluster and align correct peer programs before extracting a repair, search and align reference programs, or normalize refactorings before comparison~\cite{gulwani2018automated,wang2018search,hu2020re}; embeddings, solution-space models, and visualization propagate annotations or expose recurring strategies, while multi-function and diversified methods broaden the target beyond a single correction~\cite{piech2015embeddings,glassman2015overcode,rivers2017datadriven,yi2017feasibility,heo2023referent,choi2021automated,choi2025automated}. Generation-based systems instead condition a language model on the failing program, optionally with execution diagnostics, retrieved repair pairs, peer programs, or syntax localization~\cite{joshi2023repair,zhang2024pydex,zhang2022repairing,liu2024fastfixer,yang2024cref,orvalho2025counterexample,zhao2024peer,phung2023generating}. Unlike ours, every system we surveyed conditions or supervises repair toward an accepted solution, and most additionally require correct programs for the same problem. The closest system is LSGen, which retrieves historical repair pairs by edit information, generates, and may retrieve again~\cite{dai2026learner}. The key difference is that LSGen draws its guidance from other learners' accepted solutions for the target problem, which do not exist for a genuinely new assignment, whereas \tool mines targets from execution evidence inside observed trajectories. Since our stages change only the target and the gate, they can be combined with any of these generators.

\noindent\textbf{Learning from submission histories.} Our work belongs to a line of research that reads interaction histories rather than a single snapshot. Knowledge tracing estimates latent mastery from such histories~\cite{corbett1994knowledge,piech2015deep,ghosh2020context}, feedback research emphasizes actionable information beyond correctness~\cite{keuning2018systematic,narciss2008feedback,hattie2007power,shute2008focus}, and tutoring systems, iSnap, and language-model hints address help seeking and next-step granularity~\cite{aleven2000limitations,price2017isnap,roest2024next,xiao2024exploring,heickal2024generating}. The Zone of Proximal Development motivates support between independent and assisted performance~\cite{cole1978mind,murray2002toward,chounta2017grey,schulze2024beyond}. In contrast, \tool reads a history only to order code states by observed execution evidence: it infers no mastery, predicts no learning, and its reachability relation is narrower than the construct that motivates the name. The two readings are compatible, since a mastery estimate decides when to intervene while our stages decide what to repair toward.

\noindent\textbf{Execution-guided repair and candidate breadth.} Our controller is rooted in generate-and-validate APR, which exposed both the benefit of broad search and the risk of overfitting to tests~\cite{weimer2009automatically,legoues2012genprog,qi2014strength,smith2015cure}, and in neural repair that learns repository transformations or context-aware translation~\cite{tufano2019empirical,lutellier2020coconut,yasunaga2021break,xia2022less,jiang2023impact}. Execution-aware methods supply signals independent of model confidence: SelfAPR learns from test diagnostics, FixEval makes execution the evaluation criterion, CREF carries diagnostics through a repair conversation, and counterexample-guided repair combines generation, fault localization, and MaxSAT~\cite{ye2022selfapr,haque2023fixeval,yang2024cref,orvalho2025counterexample}. Unlike these, we use execution twice: once to define the supervision relation offline, and once to gate candidates at deployment. Repeated sampling is an established inference-scaling mechanism, because pass@$k$ rises when independent draws cover different successful programs~\cite{chen2021evaluating}; we do not claim that effect as novel but measure its exact contribution inside the controller, which also separates our portfolio from deep ensembles and model soups that aggregate probabilities or weights instead of executing complete programs~\cite{lakshminarayanan2017simple,wortsman2022model}. These mechanisms are orthogonal to target construction, so they can be combined with it.

\section{Conclusion}
\label{sec:conclusion}
Recent educational repair systems have substantially improved repair coverage, yet they all supervise repair toward an accepted solution and leave the choice of repair target uncontrolled. This paper constructs repair targets from execution evidence in submission trajectories, without a repository of correct solutions for the same problem. Our approach, \tool, iteratively mines finite improvement relations, matches outcome-equivalent peer targets, and selects a checkpoint triple whose candidates are returned through an execution gate. Under source- and count-matched training on Python and on student-disjoint Java, terminal targets increase repair coverage while intermediate targets preserve substantially more of the submitted program, and matched peer targets improve coverage further. End to end, the gated portfolio does not lead on coverage: a terminal-target triple repairs more inputs and retrieval-based generation more still, so what target construction buys is locality under a stated edit budget rather than coverage. The controller guarantees observed-test non-regression and compliance with that budget.

\section{Ethics and Research Transparency}
\label{sec:ethics}
Both corpora are archived secondary data released for research use: Project CodeNet distributes online-judge submissions with opaque user identifiers~\cite{puri2021project}, and the CodeWorkout submissions reach us through the TIKTOC release~\cite{duan2024tiktoc}. We do not attempt re-identification, we release no learner code, and we report only aggregate statistics. The study analyses archived submissions and never exposes a learner to generated feedback, so it involves no intervention with human participants; use of each corpus follows the terms of its release.

OpenAI Codex was used interactively to propose control and validation-selection designs, implement dataset builders, orchestrate experiments, develop statistical-analysis scripts, and assist manuscript drafting. The authors selected the final design and acceptance criteria, ran every job themselves, reviewed code changes, checked reported values against saved machine-readable outputs, and every cited work was checked against a retrievable source; AI-produced text is not empirical evidence.
